# ServanaClient

The Servana **customer** mobile app (Flutter). Customers browse services, book a
provider, track the job, pay, message, and leave a review.

It shares a backend with three other clients — the provider mobile app
(ServanaWorker), the provider web portal, and the admin portal — so a change to
a shared endpoint has to be checked against all four.

- **Platforms:** Android and iOS
- **State:** MobX for screens, BLoC for auth · **DI:** GetIt (`dpLocator`)
- **Routing:** GoRouter · **Storage:** Hive + `flutter_secure_storage`
- **Tests:** 983

## Getting started

```bash
flutter pub get
# provision Firebase — see below — then:
flutter run
```

## Firebase configuration

Three files are **required to build** and are **not in the repository**:

| File | How to obtain |
| --- | --- |
| `lib/firebase_options.dart` | generated by `flutterfire configure` |
| `android/app/google-services.json` | Firebase console → Android app |
| `ios/Runner/GoogleService-Info.plist` | Firebase console → iOS app |

The usual route generates all three at once:

```bash
dart pub global activate flutterfire_cli
flutterfire configure --project=<your-firebase-project>
```

Each has a tracked `.example` sibling showing the expected shape with values
replaced. Copying an `.example` into place will **not** produce a working build —
they exist so a fresh clone fails with an explanation rather than an unresolved
import.

### Why these are not committed

They were, until 2026-08-01. All three were listed in `.gitignore` — but
`.gitignore` has no effect on a file git already tracks, so the entries were
inert and the files kept being committed. A key rotation went straight back into
history as a result.

They are now genuinely untracked. If you find yourself reaching for `git add -f`
on one of them, that is the bug reasserting itself.

Firebase *client* config is public by design — it identifies the project and
authorises nothing; access is enforced by Firebase Security Rules and API-key
restrictions in the Google Cloud console. Keeping it out of the repository is
still worth doing: it stops per-environment config being baked into a branch, and
it means a rotation actually takes effect.

> ServanaWorker takes the opposite approach and tracks its Firebase config
> deliberately. Worth settling one way across all Servana clients.
