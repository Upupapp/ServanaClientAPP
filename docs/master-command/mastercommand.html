These returned 200 at 2026-08-18T16:05Z. /healthz is 200 and every gated route still answers 401, so the process is alive and authentication works. What fails is every read that queries catalog or service data.

A customer cannot browse services. A customer cannot book. This outranks every other item in this document.

TAB 01 — Restore the catalog: diagnose and fix the production 500

PhaseOwnerRiskBlocks
Stop the bleedingBackendP0 — live outageevery other tab

Objective

Return every catalog and service read to 200, establish what broke it, and leave behind a detector that would have caught it within a minute rather than a day.

Why this, and why now — measured

  • Measured 19 August 2026: /api/v1/catalog, /api/v1/catalog/summary, /api/v1/catalog/categories, /api/catalog, /api/catalog/summary, /api/services and /api/services/full all return 500. The same paths returned 200 on 18 August at 16:05Z.
  • /api/v1/search returns 200 for an empty query and 500 for ?q=aircon. The empty case short-circuits before touching the database, so the 200 is not evidence of health — it is the absence of a query.
  • /healthz is 200 and every gated route answers 401, so the process is running, the connection pool is up and authentication reaches the database. Only reads of catalog and service data fail.
  • The response is the canonical v1 envelope with a requestId, so the failure is being caught and mapped correctly — the handler is reached and throws.
  • The deploy that preceded this carried ledger-repair.sql, which rewrites the checksum_sha256 of 38 rows in servana.schema_migrations in one transaction, and the ledger it repairs includes 020-catalog-v2-expand.sql.
  • The two catalog commits in that deploy (a73b507, 3ac9548) touch providerCatalogService.ts, catalogAdmin.routes.ts and providerCatalog.routes.ts — the provider and admin write paths. Neither touches the customer read path, which is what argues for schema over code.

Method

  1. Get the real error before theorising. Pull the server log for a failing requestId — envelope.ts logs the whole exception server-side against that id while returning only INTERNAL to the caller. One log line likely names the missing relation or column outright. Every step below is a fallback for if that log is unavailable.
  2. Establish whether it is schema. On the production database, run the catalog read query by hand. A missing table, a renamed column or a type change surfaces immediately, and distinguishes "the migration did something" from "the code did something".
  3. Reconcile the ledger against reality. ledger-repair.sql updates checksums; it does not apply or roll back migrations. Confirm every row in schema_migrations corresponds to a schema state that actually exists — a repaired checksum on a migration that never fully applied is a ledger that now lies convincingly.
  4. Check 020-catalog-v2-expand.sql specifically. An expand migration should be additive and therefore safe. Verify that it was: if it renamed or dropped anything, or if it half-applied and the transaction did not cover the whole change, that is the fault.
  5. Decide roll-forward or roll-back on evidence. Roll back to the last known-good deploy if the cause is not identified within the first thirty minutes. Restoring service is not the same as understanding the fault, and it comes first.
  6. Add the detector. A synthetic check that fetches the catalog and asserts a non-empty payload, running every minute, alerting a team address. /healthz returning 200 through a total catalog outage is the precise gap: liveness is not readiness.
  7. Extend the deploy gate. A post-deploy smoke test that requests the catalog and fails the deploy on a non-200, so the pipeline refuses to leave a broken catalog running.

Acceptance gate — all must hold

  • All seven listed paths return 200 with a non-empty payload, shown before and after.
  • /api/v1/search?q=aircon returns 200 with results.
  • A written cause naming the specific migration, column or query — not "a deploy issue".
  • The synthetic catalog check is live and has been watched to fail against a deliberately broken endpoint.
  • The post-deploy smoke test is in the pipeline and demonstrated blocking a bad deploy.
  • A timeline: when it broke, when it was detected, how long customers were affected.

Guardrails

  • Do not "fix" this by editing data until the cause is known. A schema fault repaired by hand-editing rows leaves the schema wrong and the evidence gone.
  • Any migration written to repair this is itself expand-only and transactional, per TAB 05.
  • Take a database backup before any corrective DDL. The catalog is reference data; a wrong repair is worse than the outage.

Deliverable

Catalog restored, a named root cause, a one-minute synthetic detector, a post-deploy smoke gate, and a written incident timeline.

TAB 02 — Reconcile the diverged backend repository

PhaseOwnerRiskBlocks
Stop the bleedingBackendHighTAB 03, every future deploy

Objective

Bring local and GitHub main to one history, losing nothing, so that the next deploy ships a state somebody has actually reviewed.

Why this, and why now — measured

  • The backend has 47 local-only and 17 remote-only commits. This is a genuine fork, not a stale checkout: git push is rejected as non-fast-forward, and git pull without care will produce a merge nobody has reviewed.
  • Among the 47 are five verified fixes with tests, watched to fail, that have never reached production — including the fix for a defect on the most security-relevant 401 the platform emits.
  • Among the 17 are the commits deployed immediately before the catalog outage. They are in production now and are not in the local tree, so local testing cannot reproduce the live fault.
  • Two agents and a human have been committing into one working tree. During this sweep the suite count moved between runs (6,223 → 6,226 → 6,223) and a test was red purely because a file was mid-edit.

Method

  1. Snapshot first. Tag both sides — git tag pre-reconcile-local and pre-reconcile-remote origin/main — so any outcome is reversible by name rather than by reflog archaeology.
  2. Merge, do not rebase. These commits are shared between agents and some are already deployed. Rebasing rewrites hashes that other work refers to; a merge commit records honestly that two lines of work existed.
  3. Resolve conflicts with the deployed side favoured for anything currently live, and re-run the full suite after each conflicted file rather than at the end, so a bad resolution is attributable.
  4. Verify nothing was lost. Assert every one of the five known-good local commits is still an ancestor of the merge result, by hash. Assert the same for the 17 remote commits.
  5. Run the full suite on the merged tree in a clean worktree, not the shared working directory, so a concurrent edit cannot contaminate the result.
  6. Re-run the contract consumers check — the v1 contract feeds the router, the OpenAPI document, the generated registry and its own tests, and a merge is exactly where those four fall out of agreement.

Acceptance gate

  • One history, both tags reachable, zero commits dropped — proven by hash, not by inspection.
  • Full suite green on the merged tree, run from a clean worktree.
  • tests/v1-contract.test.ts green: all four contract consumers agree.
  • A written list of every conflict and how it was resolved.

Guardrails

  • No force-push. Seventeen of these commits are deployed; rewriting them detaches production from its own history.
  • Do the merge when no other agent is writing to the tree. Confirm a clean git status that stays clean for several minutes first.

Deliverable

A single reconciled history, both snapshot tags, a green clean-worktree suite, and a conflict resolution log.

TAB 03 — Ship the three verified fixes that have never deployed

PhaseOwnerRiskBlocks
Stop the bleedingBackendMediumTAB 08 rollout telemetry, TAB 10

Objective

Deploy three fixes that are written, tested, watched to fail, and sitting unshipped — and prove on production that each landed and that nothing else moved.

Why this, and why now — measured

  • Wrong successor signpost. GET /api/catalog, /api/services, /api/bookings and /api/quote all publish Link: </api/v1/bookings/:bookingId>; rel="successor-version". The catalog is not superseded by a booking read. RFC 8288 successor links are followed automatically by client generators and proxies, and five platforms are mid-migration. The cause was a parameter segment compiling to a pattern that matched any single segment under /api.
  • v1 auth failures in the legacy envelope. Every v1 401 returns {"status":"failed","code":"UNAUTHENTICATED"} with no requestId, while every 404 and 400 returns the canonical {"error":{code,message,requestId}}. A generated client gets a parser that is wrong for the single most common error class, and support cannot correlate a 401 to a log line.
  • Verifying that second fix found a further defect: verifyAuth's TOKEN_REVOKED branch writes a hybrid body carrying its own nested error key, so the translator's !body.error guard passed the most security-relevant 401 through untranslated. A revoked session is the one refusal a client must never mistake for a generic failure.
  • No security headers. No HSTS, X-Content-Type-Options, X-Frame-Options or Referrer-Policy on an origin serving five clients. The middleware exists, mounted before the CORS delegate — which is load-bearing, because a non-whitelisted origin is still served and would otherwise carry no nosniff.

Method

  1. Complete TAB 02 first. Deploying a diverged tree is how the next outage happens.
  2. Capture the production before-state with scripts/verify-deploy.sh before.
  3. Deploy through the pipeline, not by hand. TAB 01 adds a post-deploy smoke gate; use it.
  4. Run scripts/verify-deploy.sh after. It prints a verdict per fix and diffs status codes before and after, failing if any moved — the additive-only rule, measured rather than asserted.
  5. Confirm TOKEN_REVOKED and TOKEN_EXPIRED against a real revoked and a real expired token, not from source. They must arrive as distinct codes in the v1 envelope.
  6. Verify HSTS deliberately before committing to a long max-age. It is deployed without preload, which is correct — preload is close to a one-way door and every origin on the domain inherits it.

Acceptance gate

  • verify-deploy.sh after exits 0: catalog successor correct, v1 401 canonical with a requestId, all four headers present.
  • Status-code diff empty. No body, status or timing changed on any legacy route.
  • A legacy 401 body byte-identical before and after — 520 legacy routes and five clients read that shape.
  • Revoked and expired tokens demonstrated producing distinct codes.

Guardrails

  • Additive and prefix-scoped. Nothing outside /api/v1 may change shape, status or timing.
  • A 401 must not distinguish a known account from an unknown one — in status, body, timing or copy.

Deliverable

Three fixes live, a passing verify-deploy.sh transcript, and a before/after capture proving the legacy tree did not move.

TAB 04 — A deploy that cannot silently break the catalog again

PhaseOwnerRiskBlocks
Pipeline trustBackendHighTAB 16

Objective

Make it structurally impossible for a deploy to leave production serving 500s undetected, and give every deploy a rehearsed, timed rollback.

Why this, and why now — measured

  • A deploy broke every catalog read and nothing objected. The suite on GitHub main is green — 278 suites, 5,957 tests — so the fault is invisible to the tests that ran.
  • /healthz returned 200 throughout. Liveness is not readiness, and a health check that does not touch the product's primary read path will report health during a total product outage.
  • This repository has been here before: deploy.yml and release-gate.yml once ran as independent workflows on the same trigger, the gate failed, the deploy succeeded, and a red build shipped. That specific hole was closed; this is the next one along.
  • The deploy runs on a self-hosted runner on the production host and performs npm ci, migrations, npm run build and a pm2 restart in sequence. Any step can leave the previous one half-applied.

Method

  1. Readiness endpoint distinct from liveness. /readyz executes one representative read per critical domain — catalog, bookings, identity — and fails if any throws. /healthz stays as a process check.
  2. Post-deploy smoke gate. After pm2 restarts, poll /readyz and a small set of real endpoints. Non-200 fails the deploy and triggers rollback, rather than leaving a broken build serving traffic.
  3. Automatic rollback. The deploy already snapshots dist/. Wire the smoke failure to restore the snapshot and restart, then alert. Rehearse it and record the wall-clock time to recover.
  4. Synthetic monitoring independent of the deploy — an external check every minute against catalog, search and a booking read, alerting a team address. A deploy-time gate cannot catch a fault that appears an hour later.
  5. Alert on error rate, not only on deploy outcome. A 500 rate above a small threshold pages someone. The current outage was found by a sweep, not by an alert.
  6. Structured error logging with the request id surfaced where support can search it. The envelope already logs the exception against a requestId; make that reachable without shell access to the host.

Acceptance gate

  • /readyz live, and demonstrated returning non-200 while /healthz returns 200, against a deliberately broken dependency.
  • A deliberately broken build shown to fail the smoke gate and roll back automatically, with the recovery time recorded.
  • Synthetic monitoring alerting to a team-owned address, demonstrated with a real alert.
  • An error-rate alert demonstrated firing.

Guardrails

  • The smoke gate must be read-only. It may not create a booking, a message or a ticket.
  • Rollback restores code only. A migration is not rolled back automatically — see TAB 05.

Deliverable

A readiness endpoint, a blocking post-deploy smoke gate, automatic rollback with a measured recovery time, and independent synthetic monitoring.

TAB 05 — Migration safety: expand–migrate–contract, enforced

PhaseOwnerRiskBlocks
Pipeline trustBackendHighTAB 16

Objective

Make a schema change incapable of taking the product down, by enforcing the expand–migrate–contract discipline in the pipeline rather than in review.

Why this, and why now — measured

  • The prime suspect for the outage is schema. 020-catalog-v2-expand.sql is in the ledger, the deploy carried a ledger repair, and the failure signature is "auth works, catalog queries fail".
  • ledger-repair.sql rewrites the checksums of 38 migrations because they were hashed from CRLF bytes on Windows and the deploy host checks out LF. The repair is correct in itself — but it shows the ledger can disagree with reality, and a repaired checksum on a migration that never fully applied is a ledger that now lies convincingly.
  • One backend serves five clients. A contracting change — a rename, a drop, a type narrowing — breaks whichever client has not shipped yet, and the customer mobile app cannot ship quickly: it goes through two app stores.
  • The deploy applies migrations before npm run build and the restart, so a migration that succeeds while the new code fails to build leaves a schema the running code does not expect.

Method

  1. Write the rule down and enforce it in CI. Every migration is expand-only — add columns, add tables, add nullable, add indexes concurrently. Renames and drops are a separate, later migration, after every client that reads the old shape has shipped.
  2. A CI check that rejects contracting DDL in a migration not explicitly marked as a contract step with a named prerequisite release. Derive the forbidden set (DROP COLUMN, DROP TABLE, ALTER ... TYPE, RENAME, NOT NULL without a default) rather than asking review to notice.
  3. Every migration in one transaction, so a partial apply is impossible. Where Postgres forbids it — CREATE INDEX CONCURRENTLY — that migration contains nothing else and says so.
  4. Idempotent by construction. IF NOT EXISTS throughout, so a re-run after a failed deploy is safe. A migration that can only be applied once is a migration that blocks recovery.
  5. Verify the ledger against the schema, not against itself. A check that asserts each recorded migration's observable effect actually exists — the column is present, the table is present. A checksum proves the file did not change; it proves nothing about the database.
  6. Rehearse on a restored production snapshot, not on an empty database. fresh-db proves migrations run from nothing; it does not prove they run against real data.
  7. Order the deploy so the schema is compatible with both the old and new code for the duration. With expand-only migrations this is automatic, which is the point.

Acceptance gate

  • The contracting-DDL check is in CI and shown rejecting a deliberately contracting migration.
  • Every existing migration audited for transactionality and idempotence, with exceptions named and justified.
  • The ledger-versus-schema check runs against production and passes.
  • A migration rehearsed against a restored production snapshot, with timing recorded.
  • A written rollback procedure for a migration that cannot simply be re-run.

Guardrails

  • Never repair a ledger checksum without confirming the migration's effect exists in the schema.
  • No migration may run without a current backup, and the restore path must have been tested this quarter.

Deliverable

An enforced expand-only policy, a CI check watched to fail, a ledger-versus-schema verifier, and a rehearsed migration against real data.

TAB 06 — Unblock the push path and end the shared-tree collisions

PhaseOwnerRiskBlocks
Pipeline trustAllMediumTAB 03, TAB 07

Objective

Make it possible to ship at all, and stop two agents corrupting each other's measurements in one working tree.

Why this, and why now — measured

  • Both repositories reject git push: refusing to allow a Personal Access Token to create or update workflow .github/workflows/… without workflow scope. The client is blocked by flutter-ci.yml; the backend by deploy.yml, release-gate.yml and fresh-db.yml.
  • Nothing this programme produced can reach production until this is resolved. Twenty-four client commits and forty-seven backend commits are stranded.
  • Two agents share one backend working tree. During this sweep a test was red purely because a file was mid-edit, the suite count moved three times, and both agents raised the same suite-count ratchet blind to each other.
  • The suite-count ratchet is a shared mutable counter — a design that works for one writer and generates false failures for two.

Method

  1. Fix the credential. Either switch both remotes to SSH — git remote set-url origin git@github.com:… — which is not subject to the PAT scope rule, or add workflow scope to the token. SSH is preferable: it removes an entire class of scope surprise.
  2. Verify by pushing something trivial first, on a branch, before pushing 47 commits. A failed push of one commit costs nothing to diagnose.
  3. Stop sharing a working tree. Give each agent its own git worktree off the same repository. They share history and objects, and cannot see each other's uncommitted edits — which is exactly the property that was missing.
  4. Make the suite-count ratchet resilient to concurrency. Derive the expected count rather than pinning it, or assert a floor. A shared counter that two writers must both update is a design that guarantees a race.
  5. Branch protection on main. Require the gate to pass before merge, so the pipeline cannot be bypassed by whoever pushes fastest.

Acceptance gate

  • A push succeeds from this machine, demonstrated.
  • All stranded commits landed, and each verified present on GitHub by hash.
  • Each agent operating in its own worktree; a clean git status in one while the other is mid-edit.
  • The ratchet no longer produces a false failure when two suites land concurrently.

Guardrails

  • Do not strip workflow changes from commits to route around the scope rule — that silently drops CI gates, an entire release pipeline and a version pin.
  • Do not weaken branch protection to land a backlog.

Deliverable

A working push path, all stranded work landed, isolated worktrees per agent, and a concurrency-safe ratchet.

TAB 08 — The migration harness: evidence gate, rollout, rollback

PhaseOwnerRiskBlocks
Client integrationClient + BackendHighTABs 09, 10

Objective

Build the machinery that lets one capability move from legacy to canonical with evidence before, observation during and a one-step reversal after — so the waves are repetitions of a rehearsed procedure rather than improvisations.

Why this, and why now — measured

  • The canonical layer sits behind 15 capability flags, all off, all build-time. That gate was correct when v1 was undeployed. All 105 implemented v1 endpoints now answer, so the gate is no longer protecting against a missing backend.
  • The flags are deliberately not remote-configurable — a flag a server can flip is a flag an attacker can flip. That decision stays. Its consequence is that a bad wave is reversed by shipping a build, which is why each wave needs a rehearsed rollback and a bounded blast radius.
  • A prior remediation found CustomerBooking was lossier than the screen it replaced: a blind swap would have regressed totalAmount to a zero-peso display, plus serviceOptionName, branchName, the three-source status reconciliation, latitude, longitude, downPayment and numberOfPersonnel. This wave must re-run that proof, not assume it.
  • Today's outage is the argument for the observability half: a transport that starts failing must be visible as a transport failure, not as an app that quietly shows nothing.

Method

  1. Write the evidence checklist a capability must satisfy before it ships: every path answers non-404 with the contract method; both data sources satisfy one interface; the domain object from each is equal for a real account; every error code the endpoints emit is mapped; anything the endpoint set cannot serve is reported unsupported rather than silently degraded.
  2. Build the differential harness. For one canary account, call both transports for every read and assert deep equality of the domain object, not the wire payload. The wire shapes differ by design; the domain objects must not.
  3. Fail by name on a dropped field. A canonical read that adds a field is fine; one that drops a field legacy supplied is a regression, and the seven named above must each fail individually rather than as an opaque inequality.
  4. Transport observability. Every repository records which source answered; a diagnostics screen shows per-capability transport, request count, p50/p95 and error rate. Instrument through the existing analytics privacy filter — transport, capability, endpoint id, status and latency are safe; nothing resembling an identifier or a location may join them.
  5. Provision a canary account on production with real booking history, and record how to reset it.
  6. Rehearse the rollback end to end and record the wall-clock time: revert the define, rebuild, distribute, confirm the diagnostics screen reports fully-legacy. If it exceeds one hour, TAB 14 becomes a prerequisite rather than a parallel workstream.
  7. Define wave exit criteria used by every later wave: 48 hours on the canary with zero canonical-transport errors the legacy transport did not also produce, and p95 no worse than legacy by more than 20 percent.

Acceptance gate
